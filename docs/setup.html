Setup

Orbit is a pnpm monorepo: a Node server, a React web client, an Electron desktop shell and an Expo mobile app. Pick the path that fits: run the Docker stack, install the desktop app, or build from source.

Requirements

NeedFor
Node.js 22+Everything built from source (the repo's engines field).
pnpm 12The workspace (pinned in packageManager).
DockerThe default per-bot desktops, and the compose stacks.
Hermes AgentThe agent engine. The server runs one hermes gateway run per bot, the first bot included.
A model providerWhatever the primary Hermes agent uses: a subscription (for example Claude Pro/Max, which Hermes picks up from your Claude Code sign-in), an API key such as ANTHROPIC_API_KEY or DEEPSEEK_API_KEY, or a local model server such as LM Studio. See Choosing the agent's model.
Optional: an NVIDIA GPUGPU voice on Windows and Linux: 8 GB of VRAM or more with a cloud model (in testing the three voice models plus the Windows desktop used 8.4 GB; Turing / RTX 20-series or newer), Docker with the NVIDIA Container Toolkit, and about 9 GB of downloads.
Optional: COMPOSIO_API_KEY, XAI_API_KEYConnected apps; cloud voice and x_search. Both clients are lazy, so a first run boots without them.
Xcode / Android StudioOnly for native mobile builds.

Platform notes

brew install node@22 pnpm
# Docker Desktop (or another Docker engine) must be running
git clone https://github.com/raybello/orbit.git && cd orbit
pnpm install && cp .env.example .env

The desktop app ships as a .dmg and .zip for both Apple Silicon (arm64) and Intel (x64). On Apple Silicon a release can also include a native server bundle, so the app runs the stack without Docker Compose for the API (bots still use Docker desktops by default).

# Node 22 via your package manager or nvm, then:
corepack enable && corepack prepare pnpm@12 --activate
# Docker Engine with your user in the docker group
git clone https://github.com/raybello/orbit.git && cd orbit
pnpm install && cp .env.example .env

The desktop app ships as an x64 AppImage; Orbit does not install Docker on Linux, so install Docker Engine first. Linux is also the target for servers: the compose stacks and the published images (ghcr.io/raybello/orbit/app) are built for amd64 and arm64.

For GPU voice, install the NVIDIA driver and the NVIDIA Container Toolkit, then check that a container can see the GPU:

sudo nvidia-ctk runtime configure --runtime=docker && sudo systemctl restart docker
docker run --rm --gpus all nvidia/cuda:12.8.1-base-ubuntu22.04 nvidia-smi

The desktop app ships as an x64 NSIS installer and uses Docker Desktop to run the local stack. To build from source, use Docker Desktop plus Node 22 and pnpm 12; running the server under WSL2 keeps paths and the Docker socket closest to Linux.

winget install OpenJS.NodeJS.LTS Docker.DockerDesktop
corepack enable
git clone https://github.com/raybello/orbit.git
cd orbit
pnpm install
copy .env.example .env
  • Use Node 22.12 or newer. On 22.11 the prebuilt better-sqlite3 binary crashes when the server opens its database, and pnpm skips rolldown's Windows binding, so Vite and Vitest fail.
  • The repository's shell scripts and compose templates are checked out with LF line endings (.gitattributes); run them with Git Bash. The VS Code launch configs do this for you, and never pick WSL's bash by accident.
  • Hermes installs to %LOCALAPPDATA%\hermes on Windows (not ~/.hermes), and the desktop profile lives in %APPDATA%\Orbit.
  • Docker Desktop with the WSL 2 backend already includes GPU support for containers; GPU voice needs only a current NVIDIA driver on Windows.

Run the Docker stack

infra/compose has two stacks. Both run api (port 8787: the API and the built web client) and sandbox-supervisor (no port; it suspends idle bot containers so they do not hold RAM after the API stops). State lives on the orbit-data volume.

From this checkout

cp .env.example .env       # SESSION_SECRET is required
docker compose -f infra/compose/docker-compose.yml up --build
open http://127.0.0.1:8787

From published images

cd infra/compose
cp .env.images.example .env    # SESSION_SECRET: openssl rand -hex 32
docker compose -f docker-compose.images.yml --env-file .env up -d

ghcr.io/raybello/orbit/app:edge tracks main; tagged releases publish versioned tags. The server image's build context is the repository root, because it installs the whole pnpm workspace:

docker build -f apps/server/Dockerfile -t ghcr.io/raybello/orbit/app:edge .

Per-bot Docker computers bind-mount each bot's home from the host, so the folder in COMPUTER_HOME_DIR must exist at the same absolute path inside the api container. Set ORBIT_HOST_DATA and mount it at the same path, or use COMPUTER_KIND=orgo.

Build from source

pnpm install
cp .env.example .env
pnpm build        # packages, web, server, desktop shell
pnpm test         # server, web and desktop suites
pnpm typecheck    # all seven packages

For day-to-day work, run only the pieces you need:

pnpm --filter @orbit/server dev     # API on :8787, tsx watch
pnpm --filter @orbit/web dev        # Vite on :5173, proxies /api to GROKBOT_API or :8787
pnpm --filter @orbit/desktop dev    # build the Electron shell and launch it
pnpm --filter @orbit/mobile start   # Metro for the Expo client

The server serves apps/web/dist when it exists, so pnpm --filter @orbit/web build plus a server start gives you the production UI on the API port.

TargetProduction buildOutput
Webpnpm --filter @orbit/web buildapps/web/dist: a static bundle. A static host must proxy /api and /api/events to the server.
Serverpnpm --filter @orbit/server buildapps/server/dist; start with node --env-file=../../.env dist/index.js from apps/server.

Desktop app

The desktop app is an Electron shell around the server's own web build. On first launch a setup window asks where Orbit runs: This computer (it starts or attaches to a local Docker Compose stack, or the native server bundle on Apple Silicon), or a server URL. It also helps wire up Hermes. The choice is saved in the app's user data and can be overridden for one launch:

ORBIT_WEB_URL=http://localhost:5173 pnpm --filter @orbit/desktop run dev
# or: electron . --server=https://orbit.example.com

On first run the app checks for, and offers to install, what the local stack needs: Hermes Agent when it is missing; Docker Desktop on macOS and Windows when Docker is missing (on a Mac it downloads the build for your chip, checks Docker Inc's signature, copies it to Applications and starts it); and on the native Mac stack, Apple's container runtime (its signed .pkg, checked against a pinned SHA-256 and Apple's Developer ID signature before macOS asks for your password). The builds are not code-signed yet; the install guide shows the one-time steps to open them.

For testing, ORBIT_USER_DATA_DIR runs the app with a separate profile, ORBIT_STACK_DIR gives it a separate stack folder (its compose files and .env), and ORBIT_IMAGE_TAG picks the server image tag (for example edge before a release has published its own, or a tag you built locally: a tag that exists locally is used even when the registry has none).

Installers are published to GitHub Releases by desktop-release.yml on v* tags, and the app updates itself with electron-updater. Two scripts speed up local work: scripts/dev-rebuild-loop.sh rebuilds the app image, recreates the stack and relaunches Electron; scripts/dev-vite.sh runs Vite against the running stack when only the UI changed.

Build the installers yourself

scripts/build-installer.sh builds an installer the way the release workflow does, without publishing anything. Output lands in apps/desktop/out, followed by each file's size and SHA-256. The builds are unsigned unless you set CSC_LINK / CSC_KEY_PASSWORD.

Mobile app (iOS and Android)

pnpm --filter @orbit/mobile start          # Metro; open in a dev build
cd apps/mobile && npx expo run:ios         # or: npx expo run:android
eas build --profile production --platform all

The API base comes from EXPO_PUBLIC_API_URL (baked into extra.apiUrl at build time) and can be changed at runtime on the server screen. The sign-in token is kept in expo-secure-store. A release build must use https: the config throws rather than ship a cleartext public URL. A simulator reaches a server on the same Mac at localhost.

Install on a remote computer (Orgo)

  1. On your machine, build and package the server bundle (or use a release bundle), then copy it and scripts/install-on-computer.sh to the computer.
  2. In Orgo, create a public URL for port 8787 on that computer.
  3. On the computer, as root: 
    PUBLIC_URL=https://<name>.orgo.dev ORGO_COMPUTER_ID=<uuid> ALLOWED_EMAILS=you@example.com \
KEYS_FILE=/root/keys.txt PRIMARY_CDP_URL=http://127.0.0.1:9333 \
  bash install-on-computer.sh hq-app.tgz
    The script installs to /opt/hq, adds one supervisor program, and leaves Hermes alone. Running it again with a newer archive upgrades in place.
  4. Give the main agent the app's tools: python3 /opt/hq/app/scripts/add-hq-to-hermes.py adds an mcp_servers.hq entry to Hermes' config.yaml (--remove takes it out).
  5. Open the public URL and sign in.

Wiring up Hermes

  • The first bot is the primary agent. Its home is ENGINES_DIR/primary and its API server asks for PRIMARY_ENGINE_PORT (8642) first. On first boot the server imports the model keys, model config, persona, memories and skills of your own Hermes (HERMES_IMPORT_FROM, default ~/.hermes) into it once; sign-ins and messaging tokens are never copied.
  • Every other bot gets a managed home under ENGINES_DIR/<botId> (keep it outside ~/.hermes) and a gateway on a port from ENGINE_PORT_BASE (8650) upward.
  • Every engine reaches the app's tools over loopback at /mcp/<botId>; the primary's is /mcp/primary. The server writes that hq entry into each home itself.
  • Hermes' home is ~/.hermes on macOS and Linux and %LOCALAPPDATA%\hermes on Windows. The gateway's API server listens on :8642.

Choosing the agent's model

Every bot runs on the model its Hermes home is set to. Set the primary agent's with hermes model (or hermes setup); new bots inherit it, and each bot's Engine panel can change it later.

PathSetupNotes
Anthropic Claude (recommended)hermes model → anthropic → claude-sonnet-4-5. Credentials, in the order Hermes looks for them: ANTHROPIC_TOKEN / CLAUDE_CODE_OAUTH_TOKEN, then ANTHROPIC_API_KEY, then a login added with hermes auth add anthropic, then your Claude Code sign-in (~/.claude/.credentials.json, so being signed in to claude is enough).The fastest path, and the one to use with GPU voice on an 8 GB card: the GPU only has to hold the voice models. hermes auth status anthropic lists only logins Hermes stores itself, so it can say "logged out" while the Claude Code sign-in works. Check your provider's terms before running an agent on a consumer subscription.
Other cloud providershermes model, plus the provider's key in the Hermes home's .env (for example DEEPSEEK_API_KEY), or a subscription sign-in.Managed bots inherit the primary's provider and keys.
Local model (LM Studio, Ollama…)In config.yaml: provider: lmstudio, base_url: http://127.0.0.1:1234/v1, and set context_length to what you loaded the model with.Hermes assumes a 64K context unless you set it. Loading a model alongside GPU voice needs about 16 GB of VRAM between them, and avatar video arrives later because the two share the GPU.

Voice-call turns run at low reasoning effort whatever the bot's setting, because thinking tokens are silence on a call.

Connecting apps with Composio

Orbit reaches Gmail, Google Calendar, Google Sheets, Google Docs, Slack, GitHub and hundreds of other apps through Composio. Composio holds the OAuth connections; Orbit holds one API key for your Composio project and asks Composio to run each action. You do not register an OAuth client with Google or anyone else: Composio's managed sign-in does that for the apps that offer it.

How it works

  1. One key per Orbit server. COMPOSIO_API_KEY names your Composio project. Everyone who signs in to that server connects their own accounts inside it.
  2. One Composio user per Orbit user. Orbit uses your Orbit user id as the Composio user id, so your connections are yours and every bot you own can use them. Another person on the same server connects their own accounts.
  3. Connecting. The Connect apps window (or a bot's Connect card) asks Composio for a sign-in link and opens it. You sign in to the app on Composio's page, and Composio sends your browser back to SERVER_URL/api/apps/callback, which tells the waiting bot to carry on.
  4. Bots call apps through the app's MCP server. Each bot's Hermes reaches Orbit's hq MCP server, which offers Composio's tool router: COMPOSIO_SEARCH_TOOLS to find an action and COMPOSIO_MULTI_EXECUTE_TOOL to run it. Every call passes through Orbit first, which is where approvals happen.
  5. Approvals. Reads run at once and show as a line in the chat. Anything that writes waits on a card. Gmail, Calendar, Sheets and Docs get review cards you can edit before you allow them (see Google Workspace). Always on a card lets that one bot run that action without asking; it is off until you choose it, and you can take it back in settings under Always allow.
  6. Event routines. A routine on a Composio trigger (for example "a new Gmail message") is delivered to the server over Composio's realtime connection, so it needs no public URL.

Set it up

  1. Get a key. Sign up at platform.composio.dev, create a project (one per Orbit server keeps people apart), and copy its API key from the project settings.
  2. Give it to the server and restart it:
    • Docker or from source: COMPOSIO_API_KEY=… in the repo's .env.
    • Desktop app: the same line in its stack .env (on macOS ~/Library/Application Support/Orbit/stack/.env; ORBIT_STACK_DIR moves it), then quit and reopen Orbit.
  3. Check the callback address. SERVER_URL must be the address your browser uses to reach the server, because Composio sends you back there after you sign in. On your own computer the default (http://localhost:8787) works. On a remote server, set it to the server's public https URL.
  4. For Google Calendar in Orbit's calendar, set DB_ENCRYPTION_KEY (openssl rand -hex 32). Synced events are stored encrypted with it; without it the calendar says so and shows only Orbit's own events. The desktop app sets one for you.
  5. Connect your apps. Sign in to Orbit, open Connect apps, search for Gmail (or any app) and choose Connect. When the window says "Connected", close it; the app shows as connected and every bot is told what it can now do there. To use Google Calendar, Sheets or Docs, connect each one: they are separate apps in Composio.
  6. Try it. Ask a bot "what's on my calendar this week?" (a read, no card) and then "draft an email to me saying hello" (a Gmail draft card).

Optional

  • Expired connections: Orbit checks connections in the background and puts a Reconnect card in front of the bot that hit an expired one. To hear about it sooner, give the server a public URL, add a webhook in your Composio project pointing at SERVER_URL/webhooks/composio, and set its signing secret as COMPOSIO_WEBHOOK_SECRET.
  • Your own OAuth app: to show your own app name on Google's consent screen, create an auth config with your own OAuth client in the Composio dashboard. Orbit uses whatever auth config the project has.
  • Disconnecting: Connect apps → the app → Disconnect. Disconnecting Google Calendar also deletes its synced events from Orbit.

When it does not work

What you seeWhy, and what to do

GPU voice (audio.cpp)

GPU voice runs a bot's calls on an NVIDIA GPU through an audio.cpp server: OWSM speech recognition, LFM3-Audio speech in 38 voices, and SoulX-FlashHead animating a portrait you upload, lip-synced to the reply. Hermes stays the brain. Orbit ships the server as a Docker sidecar, ghcr.io/raybello/orbit/audiocpp, with a Caddy HTTPS front door.

PlatformGPU voice
Windows, Linux + NVIDIAOpt-in from the desktop app. Nothing is downloaded until you click Install.
macOSNot offered: there is no CUDA, and no Apple-silicon build of the sidecar yet. The app sets AUDIOCPP_URL=off, hides the GPU option, and calls use on-device voice.
Any serverAUDIOCPP_URL can name any audio.cpp server: the sidecar, a native build on the host, or a GPU box on the LAN.

In the desktop app

  1. Open a bot's details panel, Activity → Voice chat, and choose GPU under Voice calls. The app names the GPU it found.
  2. Install pulls the sidecar image (about 4 GB) and restarts the stack's api pointed at it (ORBIT_GPU_VOICE=1 in the stack's .env, which turns on the compose gpu profile).
  3. Download fetches the models (about 5 GB) onto the orbit-data volume, with progress in place. Once they are loaded, the sidecar warms them up, so the first call does not pay about 15 s of CUDA setup.
  4. Pick a voice and upload a portrait (any image, cropped to 512×512), then turn on Show animated avatar during calls. Without a portrait, calls are audio-only.
  5. Call the bot from the composer. Remove takes the sidecar away again; the models stay on the volume.

From a checkout

Every mode has a VS Code launch config under orbit: GPU voice —.

SetupCommand
Docker stack + sidecarbash scripts/gpu-voice-stack.sh: docker compose --profile gpu up --build, then waits for health.
Orbit dev server on the host + sidecarbash scripts/gpu-voice-stack.sh sidecar: audio.cpp on 127.0.0.1:8080, which is AUDIOCPP_URL's default, so pnpm --filter @orbit/server dev finds it.
Docker stack + a native audio.cpp on the hostNATIVE=1 bash scripts/gpu-voice-stack.sh (the api gets http://host.docker.internal:8080).

The sidecar compiles audio.cpp from source with CUDA and cuDNN. gpu-voice-stack.sh builds only for your GPU's architecture, read from nvidia-smi (about 10 minutes); the published image covers sm_75 to sm_120. Models download with Download in the voice settings, or set AUDIOCPP_AUTO_DOWNLOAD=1 to fetch them at boot. Only one audio.cpp server fits on a 16 GB card, so stop a native one before starting the sidecar.

Calls from a phone or another computer

Browsers allow the microphone only on https:// or localhost. The sidecar's Caddy serves Orbit over HTTPS on :8444 (and the audio.cpp WebUI on :8443) with its own certificate authority:

AUDIOCPP_TLS_HOSTS="localhost 127.0.0.1 192.168.1.20" AUDIOCPP_HTTPS_BIND=0.0.0.0 \
  bash scripts/gpu-voice-stack.sh sidecar
# then open https://192.168.1.20:8444 on the phone and accept the certificate warning once

Use your computer's LAN address. Opening the page by IP works: Caddy picks the certificate for the first non-loopback host. The CA lives on the data volume, so the warning comes back only if the volume is deleted. With the sidecar only, ORBIT_HTTPS_UPSTREAM (default http://host.docker.internal:5173) is the Orbit it fronts.

How fast it is

Measured on an RTX 5070 Ti with Hermes on Claude Sonnet 4.5, from the moment you stop talking: transcript at about 1.0 s, first reply audio at about 2.3 s, and avatar video at 5 to 6 s. Replies are spoken a sentence at a time while the agent is still writing, and the next piece is generated while the previous one plays. Talking over the bot interrupts it. The call protocol and design notes are in docs/voice-audiocpp.md.

Troubleshooting

  • The server exits at start: SESSION_SECRET is missing.
  • Apps or voice say "not configured": set COMPOSIO_API_KEY (see Connecting apps with Composio) or XAI_API_KEY, or install the local voice models.
  • A bot has no screen: check Docker is running and that COMPUTER_HOME_DIR exists at the same path inside the API container.
  • The primary bot cannot use the app's tools: confirm its config.yaml has the hq MCP entry pointing at a URL it can reach.
  • GPU voice is missing from the settings: the desktop app offers it only on Windows and Linux when nvidia-smi finds a GPU. On macOS it is hidden on purpose.
  • GPU voice says "not answering" or shows an audio.cpp error: run bash scripts/gpu-voice-stack.sh logs. The settings show the server's own reason when it exits (for example "out of memory"): another model, a native audio.cpp server or a local LLM may be holding the VRAM.
  • The first GPU call is slow: after a start the sidecar warms the models for a minute or so in the background; calls are fast once the settings show it ready.
  • A phone cannot use the microphone: open Orbit over https://<lan-ip>:8444, not plain HTTP, with that address in AUDIOCPP_TLS_HOSTS, and accept the certificate warning.
  • The stack fails with SANDBOX_SUPERVISOR_TOKEN missing: the stack's .env was damaged. Delete it and let the desktop app write a new one, or copy .env.images.example again.
  • Health check: curl http://127.0.0.1:8787/api/health returns the version, engine and uptime.
