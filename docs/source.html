Source code

A map of the repository: what each app and package does, how the server is split into domains, the state machines that govern bots, cards and computers, the database, and the key components on each client.

The workspace is driven by pnpm and turbo: pnpm build, pnpm test and pnpm typecheck fan out to every package. CI (.github/workflows/ci.yml) runs install, typecheck, build, tests and the server smoke script on every push and pull request.

Server: apps/server/src

index.ts starts the long-running work (engines, gateways, routine and trigger schedulers, idle watchers, container recovery, voice warm-up). api/app.ts assembles the HTTP app on its own, so tests can drive every real route without booting a background process. Mount order: /api/health, the routers, then the built web app last so its catch-all cannot shadow an API route.

A turn, end to end

  1. POST /api/bots/:id/messages writes your message row and emits rows on the hub.
  2. agent/loop.ts queues the turn (one at a time per bot) and posts it to the bot's Hermes gateway at /v1/responses. For a room, agent/rooms.ts picks which members run.
  3. The engine's event stream becomes assistant message rows and tool-call rows, revised in place (updatedSeq), and live events that say what the bot is doing.
  4. When the engine calls an app tool it goes through POST /mcp/<botId>. A Composio write action without a saved policy creates an approval card and waits for POST /api/approvals/:id.
  5. Each change is emitted on lib/hub.ts, which every client receives over GET /api/events.

Domains and state machines

The rules live in small pure modules under apps/server/src/domain, tested on their own.

Bot lifecycle (domain/bot-lifecycle.ts)

A bot needs two independent things before it can work: a Hermes engine and a screen. They finish in either order, so provisioning accumulates facts until both are present.

provisioningengineKind?, engine?, screen?engine-ready, screen-assigned; → ready once both exist

Cards (domain/card-workflow.ts, core/card-service.ts)

CardEventsTerminal statuses
approvalapprove (with always), deny, expireallowed, always, denied, expired
questionanswer, dismissanswered, dismissed
connectconnect, skipconnected, skipped
draftsend, dismisssent, discarded

The wire shape (CardBody) keeps every field at every status; the machine's terminal states only keep who decided and when. card-service.ts adapts between the two.

Computer (domain/computer-model.ts)

absent → provisioning → ready (with a screen allocation table) ⇄ suspended, or error. Screens exist only on ready; a screen is free when its botId is null, and a bot keeps its screen across resumes.

Primary bots (domain/primary-bots.ts)

Being primary is a flag, not a role. At most MAX_PRIMARY_BOTS (3) at once and always at least one, so somebody can coordinate the team. promote and restore return a plan that the route applies.

Bot creation (core/bot-service.ts, core/avatar.ts)

Capacity, name fallback ("New Bot"), mode and voice-provider normalisation, and the avatar pick: an explicit shape and colour win only when the palette has them; otherwise a hash picks from a narrower palette that leaves black for the primary.

Web client: apps/web/src

React 18, Vite and Zustand. main.tsx mounts App.tsx, which checks auth, starts the event stream (lib/events.ts) and renders the shell: TitleBar, NavRail, the section view, the DetailsPanel, modals and the config layer.

  • Web and desktop: Vitest and node:test suites.
  • End to end: tests/e2e.mjs and tests/voice-call.mjs; pnpm smoke runs scripts/smoke-server.mjs.
